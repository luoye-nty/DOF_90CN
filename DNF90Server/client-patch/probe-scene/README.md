# SceneProbe（独立只读探针 DLL）

**不属于 90CN，不上生产，不碰 90CN 的任何文件。** 只读游戏内存 + 写自己的日志。

## 它要回答的问题

孵化场房间里出现的**副本门**和**「前进!!」指向**，方向和位置都属于上一个房间
（能量阻截战 218 的 191xx 图），而 op28/op29 在组队与单人之间逐字节相同
（只差 4 字节种子）—— 所以服务端没有发错对象，剩下的可能只有一个：
**客户端没拆掉上一个房间的客户端自建几何。**

要判定它，必须看到客户端**当前场景的「自建对象/通路门」容器里到底是哪一组的 id**：

| 房间 | `[pathgate pos]`（x 坐标） | 判定 |
|---|---|---|
| 孵化场 1 起始房 `17183(3,0)` 同族 | 0 / 448 / 448 / 896 —— **有一扇贴左墙** | 是孵化场自己的 |
| 218 的 191xx 房（如 `19100(0,0)`） | 647 / 1040 / 1165 / 879 —— **左墙没有门** | 是 218 的残留 |

同理还有 `.map` 里的 `[passive object]`（218 的 19123 有 21 个：岩石 18750/18753/18755/
19167-19169、门 dummy 18895 + 岩浆地砖；孵化场起始房只有 1 个 19117）。

## 当前状态：**钩子表为空，先只验证通路**

`SceneProbe.cpp` 的 `g_hooks[]` 是空的。注入后它只做三件事：
写启动行、打印宿主基址、声明不 patch 任何东西。

这是故意的：**目标函数地址必须先用反汇编确认**，并把该处原始字节原样抄进
`expected`。地址靠推测填进去可能直接崩客户端 —— 探针存在的意义是取证，
不是引入新的不确定性。

反汇编工具：`tools\_raid_lib.py`（`dump(va, n, label)` 反汇编并打印、
`va2off` / `off2va` / `find_dword_refs`），镜像基址 `0x00400000`。

## 安全设计（为什么注入它不会搞坏客户端）

1. **只读**：不写游戏状态、不改任何字段，只读内存 + 写 `SceneProbe.log`。
2. **字节签名校验**：`InstallInlineHook` 打补丁前比对 `expected`，
   不匹配立刻放弃并记日志（含实际字节与期望字节），**绝不半打补丁**。
3. **基址校验**：宿主模块基址不是 `0x00400000` 就放弃安装任何钩子。
4. **SEH**：每次读内存都包在 `__try/__except` 里，读失败返回 0，不向外抛。
5. **日志独立**：写 DNF.exe 同目录的 `SceneProbe.log`，不碰
   `90CN_trace.log` / `RaidProbe.log`，可与 90CN 同时注入。
6. **打不开日志就静默退出**，不影响游戏启动。

## 构建

x86 / v142 / DynamicLibrary（与 90CN 工程同配置，注入行为一致），不依赖 MinHook 等第三方库：

```
msbuild client-patch\probe-scene\SceneProbe.vcxproj /p:Configuration=Release /p:Platform=Win32
```

产物：`client-patch\probe-scene\build\SceneProbe.dll`

## 注入后的读法

`SceneProbe.log` 里会逐条记录每个房间加载后容器里的对象 id 与通路门坐标。
判定规则就用上表：**如果孵化场起始房里出现 191xx 那一组的 id/坐标，残留即成立**，
且这份数据可复现、可反证（换个房间进、或单人进，对照即可）。
