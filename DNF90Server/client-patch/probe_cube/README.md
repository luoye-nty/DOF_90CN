# CubeProbe —— 装扮合成器 / 梦想合成器(op1119) 只读探针

> 目的：把"梦想装扮合成器按下去以后客户端到底发了什么、在等什么、认不认回包"
> 这三件事从客户端内部取到实证。服务端日志只能看到"收到了 op1119"，看不到
> 客户端之后为什么不响应。
>
> **它不是 90CN。不修改、不链接、不依赖 90CN.dll / 90CNLua.dll 的任何文件或符号，
> 两个模块可以同时存在。** 它只做一件事：在三个函数头上挂自己的日志钩子。

## 2. 它挂哪三个点（都只读）

| RVA | 函数 | 为什么挂它 |
| --- | --- | --- |
| `0x02FAAFE0` | C2S 上层包体编码边界 `sub_33AAFE0` | 客户端**发出去**的每个包都会经过这里：opcode、包体、调用栈 |
| `0x02FAB0A0` | S2C 上层包体解码边界 `sub_33AB0A0` | 服务端**发回来**的每个包都会经过这里：opcode、包体 |
| `0x01E62430` | 分发查表 `sub_2262430` | 客户端每次要把回包交给处理器时都会查这张表；查表结果 = "这个 opcode 客户端认不认" |

另外**只读调用**两个注册表单例 getter（`0x01E628F0` class-1 / `0x01E62A80` class-0），
把整张"客户端认识哪些回包"的清单（opcode → 处理器地址）转储出来。
这张表就是判断"梦想合成器等的是哪个号"的关键证据。

### 与 90CN 共存
90CN.dll 在生产客户端上已经勾了上面第 1、2 个函数头（写 E9）。
探针安装时先读目标首字节：

* 首字节是 `E9` → 说明已有钩子（正常就是 90CN）。探针只覆盖这 5 字节，把链的
  下一跳记成 90CN 那个 E9 的目标，自己干完活 `jmp` 过去 —— **90CN 行为完全不变**。
  日志里会写 `mode=chain 下游钩子=90CN.dll+0x...`。
* 首字节是原生前导 → 探针把前导整指令搬进跳板，干完活跳跳板再回函数体。
  日志里会写 `mode=native`。

所以**必须在 90CN 之后注入**（90CN 随 ijl15 代理在进程启动时加载，人工注入本来就在后面）。

### 安全边界
1. 只读：不改游戏状态、不改包体、不塞包、不改任何字段。
2. 唯一的写入是三个函数头各 5～7 字节的跳转，且**逐字节校验前导后才写**；
   不匹配就拒绝并记 `REFUSED`（没有任何副作用）。
3. 每次读客户端内存都用 SEH 包住。
4. 探针自己崩了不会静默 —— 日志里最后一行就是进度。

## 3. 自检（已跑过，全绿）

```
build_cube_probe_selftest.bat
```

在自己进程里用"手工合成的机器码"当目标函数，把四条路径各跑一遍：

* native 跳板：钩子装上后原函数照常执行、返回值不变
* `E9` 链：模拟 90CN 已经勾过，确认下游钩子照常被调用、返回值透传
* 版本不符：前导不匹配时必须拒绝打补丁
* 查表转发器：`__thiscall` 的 `ecx`(注册表) 与栈上 opcode 必须和真实调用一致

20 项全过。**这保证的是 naked 转发器的 esp 偏移、跳板、E9 链都没写错**，
而不是"探针在真实客户端上一定对" —— 后者要靠下面的预检 + 现场日志。

## 5. 现场操作单

1. 正常启动客户端、登录、**站在城镇里**（不要在副本/加载中注入）。
2. 用你平时那个注入器，把 `CubeProbe.dll` 注入 `DNF.exe`。
3. 等 2 秒，打开 `D:\test\地下城与勇士\CubeProbe.log`，确认开头有：
   * `========== CubeProbe 启动`
   * `HOOK 'c2s-encode...' INSTALLED`
   * `HOOK 's2c-decode...' INSTALLED`
   * `HOOK 'dispatch-lookup...' INSTALLED`
   三行都是 `INSTALLED` 才继续；有 `REFUSED` 就停下来把日志发我。
4. **先用一个能用的合成器（普通装扮合成器）做一次合成** —— 这是对照组。
   日志里必须出现 `C2S op=99 TRIGGER`（证明钩子确实能看到合成器请求）。
5. **再用梦想装扮合成器做一次** —— 日志里必须出现 `C2S op=1119 TRIGGER`
   并紧跟着 `ARM seconds=25`。
6. 出现 `ARM` 之后**什么都别按，等 25 秒**（窗口里所有收发与查表都会记下来）。
   就算鼠标卡住也别急着关，卡住本身就是证据。
7. 关掉游戏，把 `CubeProbe.log` 发我。

> 第 4 步很关键：如果连普通合成器的 `C2S op=99` 都看不到，说明这个号段不走
> 上层包体编解码边界，那就要换钩子点 —— 一看日志就知道，不用猜。

注入后不用管它，热键 **F9** 可以随时手动重新转储一次注册表（会在日志里写
`HOTKEY`）；不想要热键就把 `CubeProbe.ini` 里 `hotkey_vk` 改成 0。

## 6. 日志怎么读（判据）

| 日志行 | 说明 |
| --- | --- |
| `HOOK '...' mode=chain 下游钩子=90CN.dll+0x...` | 90CN 的钩子被正确串在探针后面 |
| `C2S op=1119 len=144 TRIGGER body=... stack=[0]DNF.exe+0x...` | 客户端发出的原始请求 + **谁发的**（栈顶就是发送方，之后可以直接反汇编它看"发完在等什么"） |
| `ARM seconds=25 cause=C2S-op1119` | 全量窗口开始 |
| `S2C op=N handler_cls=1 handler=DNF.exe+0x...` | 客户端收到 N 号包，并且**它有 N 号的处理器**（地址给出后可直接反汇编出期望格式） |
| `S2C op=N handler=NONE` | 客户端**没注册** N 号处理器 → 这个包它根本不会处理 |
| `LOOKUP cls=1 op=N handler=DNF.exe+0x... / handler=NONE` | 客户端主动去分发 N 号包时的查表结果 |
| `REG cls=1 op=1119 cb=...`（或整张表里没有 1119） | "客户端认识哪些回包"的完整清单 |
| `HOOK '...' REFUSED: 目标字节不匹配` | 客户端版本与探针不符，没有做任何写入 |

**三种可能的结论，日志会直接指出来：**

* 若 `REG` 表里根本没有 1119、`LOOKUP` 里也从不出现 1119 →
  客户端压根没等这个回包，问题在客户端本地流程（UI/资源），不在协议。
* 若有 1119 的处理器 → 把它地址发我，我直接反汇编出服务端该发什么字节。
* 若客户端在等的是**另一个号**（例如 99 或某个 1128/1133 号段）→
  `LOOKUP` 行会显示它在 ARM 窗口里查了哪个号，那就是服务端该回的号。

## 7. 配置（`CubeProbe.ini`）

```ini
trigger_opcodes=1119, 99      ; 见到这两个号就进全量窗口 + 打调用栈
watch_opcodes=1119,99,63,80,81,82,247,248,249,250,261,1100,1112,1128,1133,45,46,47,48,49,50
arm_seconds=25                ; 全量窗口长度
log_all_c2s=1                 ; 非窗口期也记 C2S（只记 opcode+长度）
log_all_s2c=0                 ; 非窗口期是否也记 S2C（默认关）
full_body_bytes=512           ; 窗口/触发时的包体打印上限
brief_body_bytes=48           ; 其它情况
stack_frames=14               ; 调用栈帧数，0 = 不打
lookup_resolve=1              ; 查表钩子里顺手解析"有没有处理器"（纯只读）
lookup_log_all=0              ; 所有查表都记（量很大，只在专门排查时开）
registry_dump_on_start=1      ; 启动 6 秒后转储一次注册表
registry_scan_max=4096        ; 转储扫描范围
hotkey_vk=120                 ; F9 = 手动转储；0 = 关
```

日志变大时优先调小 `registry_scan_max`、把 `log_all_c2s` 设为 0。
